## Why

The site already publishes machine-readable surfaces for crawlers and clients — `robots.txt`, `sitemap.xml`, `feed.xml`, `openapi.json`, `/.well-known/api-catalog` — but three conventional public files are missing: there is no way to report a security issue against `themkvz.com` (no `security.txt`), no human credit file, and no curated index for the coding agents that increasingly read this site as a source. `robots.txt` is also a static three-liner that predates the AI-crawler landscape and says nothing about the endpoints that now exist, and `site.webmanifest` ships with empty `name` and `short_name`, so install prompts and Android task-switcher entries render nameless.

## What Changes

- Add `/.well-known/security.txt` per RFC 9116: served over HTTPS as `text/plain; charset=utf-8`, with `Contact`, `Expires`, `Canonical`, and `Preferred-Languages`. Generated by a route so `Expires` rolls forward automatically and the file cannot go stale.
- Add a `/security.txt` legacy alias that permanently redirects to the well-known path, as the RFC allows for backward compatibility.
- Add `/humans.txt` crediting the author and the stack, referenced from every page's `head` with `rel="author"`.
- Add `/llms.txt` following the llmstxt.org format — H1, blockquote summary, and H2 link sections indexing the site's pages, published workbench artifacts, and machine endpoints. Generated from the content layer so it never drifts from what is published. This is a Business-to-Agent surface, not an SEO signal: no major crawler reads it, and the proposal does not claim ranking benefit from it.
- Replace the static `public/robots.txt` with a generated route that keeps the blanket `Allow: /`, names AI crawler user-agents as explicit allows so the policy is legible rather than accidental, and advertises the sitemap.
- Fill in `name` and `short_name` in `site.webmanifest`, and reference the manifest from the document head.
- Advertise the new files from `head` (`rel="author"`) and from `llms.txt`; do **not** list `.txt` endpoints in `sitemap.xml` — a sitemap lists indexable pages, and adding non-HTML resources to it is a common mistake, not a best practice.

Non-goals: no PGP key or file signing; no vulnerability-disclosure policy page; no `ai.txt`; no broad technical-SEO audit. The SEO work here is limited to what these files touch.

## Capabilities

### New Capabilities
- `discovery-files`: the contract for the site's public plain-text discovery surfaces — `security.txt`, `humans.txt`, and `llms.txt` — covering their addresses, content types, required fields, freshness, and how they are advertised.

### Modified Capabilities
- `seo`: the "Sitemap and robots" requirement gains an explicit, legible crawler policy and moves `robots.txt` from a static asset to a generated route; a new requirement covers the web app manifest's identity fields and its advertisement from the document head.

## Impact

- **New route modules** under `src/routes/`: `[.]well-known.security[.]txt.ts`, `security[.]txt.ts` (redirect), `humans[.]txt.ts`, `llms[.]txt.ts`, `robots[.]txt.ts`. All are resource routes with a `loader` and no component, matching `sitemap[.]xml.ts` and `feed[.]xml.ts`.
- **Deleted**: `public/robots.txt` — superseded by the generated route. A static file in `public/` would otherwise shadow the route.
- **Modified**: `src/constants.ts` (author/security metadata the new files read from), `src/root.tsx` (`links` gains `rel="author"` and the manifest), `public/site.webmanifest`.
- **No new dependencies.** No content-layer schema changes. No changes to page rendering or existing loaders.
